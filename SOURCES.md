### `apify.store.actors`

**Apify** (first party) · weekly · active

Every actor in the Apify store, weekly: usage counters, pricing model, categories, review and bookmark counts.
WHY THIS IS WORTH CAPTURING. `totalUsers30Days` is live paid demand per scraper -- how many people ran this thing last month. Nothing else in the fleet measures whether a data product has customers. But the store publishes only NOW: there is no history endpoint, no changelog, and no created date in the listing, so every number is a single frame with nothing behind it.
THE ARCHIVE DOES NOT COVER IT, MEASURED. api.apify.com/v2/store has ONE Internet Archive memento, ever. That memento holds 949 of the 48,189 actors it claimed at the time -- 2.0%. The HTML store page apify.com/store has 170 mementos, and four sampled ones held between 0 and 40 actor slugs, with totalUsers30Days present in exactly one. So no usage series exists anywhere.
WHY WEEKLY AND NOT MONTHLY, WHICH WAS THE FIRST ANSWER. Two reasons, both measured rather than preferred. First, the store carries no createdAt, so the only age signal available is FIRST-SEEN ACROSS OUR OWN CAPTURES -- and the resolution of that proxy IS the cadence. Everything appearing between two captures shares one birthday. The actors that matter are young: a stratified sample put the 1-9 monthly-user band at a median age of 104 days and the zero-user band at 323, and one competitor in a six-actor niche was NINE DAYS OLD when read. Monthly would collapse those six entries into five points and erase the order they arrived in, which is the only thing separating a land rush from a steady trickle. Second, totalUsers7Days is a SEVEN-DAY window, so weekly sampling of it is non-overlapping and independent; monthly discards three weeks in four.
WHAT WEEKLY DOES NOT BUY, STATED SO NOBODY EXPECTS IT. totalUsers30Days is a 30-day rolling window: four weekly reads share about 75% of their input, so the usage series carries roughly one independent observation per month however often it is sampled. totalUsers90Days is worse. Weekly sharpens ARRIVAL and DEPARTURE, which is the wss part. It does not sharpen usage.
THE TRAP IN FIRST-SEEN, WHICH WOULD OTHERWISE POISON A YEAR OF DATA. The store endpoint truncates: pages return items until roughly offset 15,900 and zero after, under every sort order. So an unpartitioned sweep sees a popularity-ordered SLICE, and within that slice an actor first appears when it becomes popular enough to cross the threshold -- NOT when it is created. Those are different events. First-seen is a valid age proxy ONLY inside partitions that enumerate completely. 20 of 23 categories sit under the cap and do; AUTOMATION (~29,700), LEAD_GENERATION (~24,200) and DEVELOPER_TOOLS (~21,700) do not. Age analysis is sound in the small categories and unsound in the three largest, and that is a property of the data, not a bug to be fixed later.
`total` IS NOT A DENOMINATOR. Same store, same minute, three sort orders returned 66,631 / 73,016 / 70,918, and it drifts upward during a single sweep (65,048 -> 66,630) because the store is written while it is read. Report the count of distinct ids collected and say the true size is unknown.
`count` IS NOT A COUNT EITHER. The response carries `count`, and it ECHOES THE REQUESTED `limit` -- a page returning zero items still reports count: 1000. Reading it produced two confident and opposite wrong claims about the store's size within minutes. Only `len(items)` means anything, and `limit` is a MAXIMUM: mid-range pages return 384-959 for limit=1000, so a short page is not the end of a partition. Only a zero-item page is.
PARSED BY parsers/apifyactor_v1.py, keyed on the actor `id`, which is the stable identifier; username/name can both be renamed. `listed` is emitted once per actor per capture and its absence later is the departure signal, since there is no terminal status. `categories` is SORTED before emission -- it is a set served in arbitrary order and would otherwise report a change every week.
